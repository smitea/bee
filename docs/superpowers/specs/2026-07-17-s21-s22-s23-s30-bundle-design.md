## Why this story bundle

Four small main-repo stories are nearly done at the library level but missing one or two lines of glue. This bundle closes them in a single combined plan so we can ship 4 stories' worth of value cheaply.

| Story | Current state | Gap |
|---|---|---|
| **S21** Multi-version coexistence | `PluginManager::retain` / `release` exist with auto-unload at refcount = 0 (verified in `crates/bee-registry/src/lib.rs:276–301`) | The caller never **calls** `release()` when a Job stops. The library logic is correct but the deploy/stop path doesn't wire it. |
| **S22** Tokio task wrapper + per-Task priority queue | `SchedulerPolicy` + `RuntimeScheduler` trait + 4 unit tests pass (`crates/bee-runtime/src/scheduler.rs`); `PriorityRuntimeScheduler` is `Default::default()` | The `bee.runtime.scheduler_policy` config knob is not read at startup. The CLI doesn't even instantiate a `SchedulerConfig`. |
| **S23** MLFQ default | `Mlfq` scheduler implemented + unit-tested; `SchedulerPolicy::Mlfq` variant exists | `SchedulerPolicy::default()` is `Priority`, not `Mlfq` (one-line change; ADR-0008 §3 specifies `Mlfq` as the default). |
| **S30** Secret store integration | `SecretStore` trait + `InMemorySecretStore` impl + 5 unit tests pass (`crates/bee-control/src/secret_store.rs`); `bee secret put/get/list/delete` CLI works | `BeeHostV1` C struct does **not** expose a `secret_get` FFI hook. Plugins can't read secrets through the host's KV-backed store (S43 added `kv_get`/`kv_put` but S30 needs `secret_get` which goes through the SecretStore abstraction, not the raw KV). |

## Scope

### In scope (4 small changes)

1. **S23** (1 line): Change `SchedulerPolicy::default()` from `Priority` to `Mlfq` (`crates/bee-runtime/src/scheduler.rs:67–73`). Refresh the `scheduler_config_default_uses_mlfq_s22_default` test (or add a new one) to lock down the new default.

2. **S22** (~30 LOC): Add config file reading to the bee binary. Read a `bee.toml` (or env vars `BEE_RUNTIME__SCHEDULER_POLICY`) at startup, parse into `SchedulerConfig`, pass to the worker setup. Without a config file, fall back to `SchedulerConfig::default()` (which is now MLFQ per S23).

3. **S21** (~20 LOC): In the Job-stop path (wherever Jobs transition from `Running` → `Completed` / `Failed` / `Revoked`), call `plugin_manager.release(plugin_id)` for each plugin the Job was using. This wires the existing `release` auto-unload logic into the lifecycle. Add a unit test that asserts the Plugin is unloaded after the last referencing Job stops.

4. **S30** (~15 LOC): Add a `secret_get` (and `secret_put` for symmetry) FFI hook to `BeeHostV1` in `crates/bee-plugin-sdk/src/lib.rs`. Add a `safe_secret_get` wrapper. The host wires these to `InMemorySecretStore`. Add a unit test asserting the round-trip works.

### Out of scope (deferred)

- **`SecretStore` backed by Raft-replicated KV** — S30's MVP is in-memory; the Raft-backed impl is 1.x. S43 added `kv_get`/`kv_put` but S30 needs the SecretStore abstraction (which adds per-tenant scoping + audit logging).
- **Plugin refcount auto-unload across cluster** — S21's auto-unload works **locally** (each Node unloads its own copies). Cross-Node unload requires network sync (`crates/bee-registry/src/lib.rs:317` has the network-sync stub).
- **Multi-version coexistence across cluster** — same as above; per-Node only.

## Decision matrix (for the user)

| Question | Choice | Notes |
|---|---|---|
| Config file format | **TOML (`bee.toml`)** + env vars (`BEE_RUNTIME__SCHEDULER_POLICY`) | Standard; matches `workspace.metadata` style |
| Scope of S30 hook | **`secret_get` only** | `secret_put` is admin-only; S30's plugin use case is read-only |
| Wire `release` for all plugin operations or just Job stop? | **Just Job stop** | The acceptance criterion is "Old versions auto-unload when all referencing Pipelines stop"; Job stop is the right hook |

If any of these decisions should change, the user can override during the spec review.
